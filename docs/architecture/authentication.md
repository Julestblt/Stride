# Authentication

The public `/sign-in`, `/sign-up`, `/forgot-password` and `/reset-password` routes use feature-local React forms and server actions. Supabase access lives under `src/server`. Successful password sign-in, confirmed email callbacks and password changes return to the existing `/`; onboarding and a protected dashboard are outside this change.

Email and password input is validated with Zod before provider calls. New passwords require 10–128 characters, matching confirmation, and must not contain the email's local part (three or more characters) or match a small local list of common/repeated passwords. The strength meter describes this local length policy, not an entropy estimate or a breach check. Configure Supabase's password policy to at least the same minimum; leaked-password protection is a separate provider setting and is not claimed by the UI.

## Environment and provider setup

Set `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` together. Never use a service-role or secret key. Set server-only `SITE_URL` to the trusted application origin: `http://localhost:3000` for local development, an HTTPS origin for deployment. It cannot contain a path, credentials, query or fragment. Email flows fail safely when it is missing or invalid. Password sign-in does not require it. Signup also requires this origin and uses a confirmation redirect; the response determines whether the user has a session or needs to check their inbox.

In Supabase Auth URL Configuration, set Site URL to that origin and allow the callback URLs `<origin>/auth/callback?next=/&sb_flow_id=*` and `<origin>/auth/callback?next=/reset-password&sb_flow_id=*`. The wildcard is limited to the SDK-generated flow identifier; the origin, path and destination remain explicit. Maintain separate entries for trusted development and production origins; avoid broad production wildcard redirects.

The default flow is PKCE: requests originate in a server action, the verifier is written to an HTTP-only cookie, and `/auth/callback` exchanges the returned `code`. Open the email in the same browser that requested it. The installed SDK’s experimental `appendPkceFlowIdToRedirects` option keeps overlapping requests separate; the callback validates the returned 32-character hexadecimal `sb_flow_id` before selecting its verifier. Keep this behavior covered when upgrading the SDK. See [Supabase PKCE guidance](https://supabase.com/docs/guides/auth/sessions/pkce-flow). Implicit-flow fragment tokens are not accepted. If configurable email templates are used, an alternative template can link to `<origin>/auth/callback?token_hash={{ .TokenHash }}&type=recovery` for recovery, `type=signup` for signup or `type=magiclink` for sign-in. The callback supports these token-hash types and `email`, verifies them through Supabase, and allows only `/` or `/reset-password` as success destinations. Token-hash links can work across browsers. New Free projects using default SMTP may not allow template customization; configure custom SMTP before relying on customized templates.

Enable email auth, set confirmation requirements deliberately, configure production SMTP and sender identity, and review email rate limits and token expiration in Supabase. The default provider can restrict recipients to organization members and is unsuitable for public launch. Test confirmation, recovery and magic links in the intended deployment after configuring exact allowlists and email delivery. Automated tests use an isolated local HTTP auth-provider fixture and unit mocks and never send real email or create accounts. No provider configuration is changed by the implementation.

## Sessions and recovery

The remember-device control applies to password and magic-link sign-in. Auth cookies and the persistence preference are HTTP-only, same-site lax and secure on HTTPS and in production. Unchecked sign-in uses session cookies, checked sign-in retains provider expiry. The preference survives callbacks and refreshes; signup and recovery default to session cookies. Browser session restoration can preserve session cookies, so closing the browser is not a guaranteed logout. There is no browser Supabase client. Next's proxy refreshes sessions and retains provider cookies and cache headers. Auth responses are private and not cached. Sensitive password updates validate the current user with `getUser`, including confirmed email, rather than trusting cookie contents or `getSession` alone.

The password route also accepts an already signed-in, confirmed account as an authenticated password-change flow; it does not claim a separate recovery-only authorization grant. Anonymous users must follow a valid link or sign in.

Recovery displays three stages but only enables the stage supported by actual state. Inbox feedback follows a provider response and avoids confirming account existence. Resend has a 60-second UI cooldown; provider rate limits remain authoritative and the UI timer is not a security control. Link validity is determined by Supabase, with no hardcoded expiration promise. Password updates request sign-out of other sessions while preserving the current one. If revocation fails, the UI reports that the password was saved and gives a continue link. Existing access tokens can remain valid until expiry.

## Launch gaps

The approved visual copy refers to upcoming coaching and Garmin capabilities; these screens do not implement those capabilities. Terms and privacy policies are not published. Accessible disclosures state that limitation rather than linking to nonexistent pages or claiming consent to missing policies. Publish the policies and replace the disclosures before public launch. Full production email delivery and external dashboard configuration require a deployment-specific operational check.
