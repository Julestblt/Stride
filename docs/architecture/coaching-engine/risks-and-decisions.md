# Risks, assumptions and decisions for the product owner

- Status: Proposed (RFC #86)
- Routine engineering choices were made in this RFC and recorded in ADRs 0007–0012. The decisions below change product behavior, safety responsibilities, recurring costs, provider commitments or sensitive-data handling, so they belong to the product owner.

## Risks

| Risk                                                                                           | Likelihood | Impact | Mitigation                                                                                                                                  |
| ---------------------------------------------------------------------------------------------- | ---------- | ------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Plans are valid but not better than a generic template                                         | Medium     | High   | Evaluation rubric with a human coach; pilot outcomes; downgrade or upgrade models based on evidence                                         |
| A plan contributes to an injury or illness                                                     | Low–medium | High   | Spike and health rules, referral copy, no medical claims, clinician review, conservative defaults with injury history, clear athlete agency |
| Thresholds rest on weak or observational evidence                                              | High       | Medium | Evidence grades on every rule; conventions labeled; thresholds versioned and revisited with pilot data                                      |
| Cross-athlete data exposure                                                                    | Low        | High   | RLS reads as the athlete, scoped tools, private write functions, isolation and injection tests                                              |
| Prompt injection through imported or typed text                                                | Medium     | Medium | Data envelopes, no exfiltration tools, validation independent of model reasoning                                                            |
| Cost overrun                                                                                   | Low–medium | Medium | Hard run caps, quotas, monthly budgets, kill switch, Batch API for reviews                                                                  |
| Approval fatigue from too many proposals                                                       | Medium     | Medium | One monitor-driven proposal per day, weekly bundling, D3 later                                                                              |
| Provider outage, model deprecation or behavior change                                          | Medium     | Medium | Gateway port, pinned model ids, evaluation gate before upgrades, deterministic degraded mode                                                |
| Garmin sync delays or gaps                                                                     | Medium     | Medium | Data-quality gate, freshness in every proposal, change feed (G8)                                                                            |
| The worker role or pooler assumption fails                                                     | Medium     | Low    | Phase 2 spike first; fallback to a direct connection or a constrained server key as in #42                                                  |
| Worker packaging with `server-only` modules                                                    | Medium     | Low    | Decide the entrypoint build in the first worker spec; run with the `react-server` condition                                                 |
| Regulatory exposure (GDPR special-category data, AI Act transparency, medical-device boundary) | Medium     | High   | D1 and D2 before pilot; AI disclosure in French; legal review of copy and intended purpose                                                  |
| Shared Supabase project role still unconfirmed                                                 | Medium     | Medium | Migrations stay behind the existing approval checkpoint; staging project for live validation                                                |
| Operations depend on one maintainer and a homelab                                              | Medium     | Medium | No new stateful service; runbooks; kill switch                                                                                              |

## Open questions for domain experts

- Pain and illness thresholds, red-flag list and return-to-running progression (clinician).
- Template numbers per event family, long-run caps for ultra distances, masters-athlete adjustments, and the workout library (running coach).
- Whether single-session spike limits should use distance, duration or both for trail sessions with large elevation gain.

## Adjacent observation

Stride's race workspace already calls Open-Meteo for weather. Open-Meteo's terms state "You may only use the free API services for non-commercial purposes" and list subscriptions or ads as commercial use ([terms](https://open-meteo.com/en/terms), read on 2026-10-13). If Stride charges athletes, it needs a paid Open-Meteo plan. This is outside the coaching engine but is a recurring-cost item for the product owner.
