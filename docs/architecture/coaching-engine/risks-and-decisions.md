# Risks, assumptions and decisions

- Status: Accepted (RFC #86, decisions recorded in #94)
- Routine engineering choices were made in this RFC and recorded in ADRs 0007–0012. The decisions below change product behavior, safety responsibilities, recurring costs, provider commitments or sensitive-data handling, so they belong to the product owner.

## Product-owner decisions

The product owner decided D1–D8 on 2026-10-13. Stride is a personal, open-source application used by its owner and possibly one or two relatives on a self-hosted instance; several decisions follow from that context.

| ID  | Topic                             | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| --- | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Model provider and data residency | Claude through the official Anthropic API behind the swappable `ModelGateway` port. A second, OpenAI-compatible adapter stays possible and is adopted only if it passes the same evaluation suite. No EU-residency requirement.                                                                                                                                                                                                           |
| D2  | Consent and retention             | No AI-processing consent flow and no time-based retention purges. Row-level isolation per athlete stays.                                                                                                                                                                                                                                                                                                                                  |
| D3  | Automatic minor changes           | None in V1: every plan change needs the athlete's approval.                                                                                                                                                                                                                                                                                                                                                                               |
| D4  | Quotas and cost model             | No per-athlete quotas or monthly budgets for now; real consumption is observed first. Per-run technical caps (model calls, tool calls, tokens, cost, wall clock) stay as runaway protection, and usage is recorded per call.                                                                                                                                                                                                              |
| D5  | Sending workouts to Garmin        | Deferred; garmin_mcp draft G10 stays deferred.                                                                                                                                                                                                                                                                                                                                                                                            |
| D6  | Plan detail horizon               | Every week is fully detailed at plan creation. Every session has its complete structure: warm-up, repetitions, recoveries, cool-down, pace and heart-rate targets. There are no provisional weeks. The weekly review re-checks the coming week against adherence and readiness and proposes changes through the normal proposal flow.                                                                                                     |
| D7  | Provider for the existing skills  | Insights phrasing and roadbook extraction move to Claude Haiku 5.5 once the gateway exists (Phase 2), with a one-step escalation to Sonnet 5.5 when the output fails validation, then the existing deterministic fallback.                                                                                                                                                                                                                |
| D8  | Event scope and expert ownership  | No human expert reviewers. Quality and safety rely on the evidence-graded deterministic validator, conservative defaults and an automated evaluation suite with an LLM judge using a written rubric, preferably a different model than the generator. The athlete is the only human in the loop. Event scope: road 5 km to marathon and trail of every distance; plans above 60 km carry a low-confidence label instead of being refused. |

Model routing confirmed with D1: Haiku 5.5 for routing, extraction and phrasing; Sonnet 5.5 for conversation, adaptation, weekly reviews and consults; Opus 5.5 for plan design and multi-race revisions, falling back to Sonnet 5.5 at high effort when Opus is unavailable. Any task may escalate one tier when its output fails validation ([ADR 0011](../../adr/0011-model-access-and-routing.md)).

On 2026-10-14 the product owner added:

| ID  | Topic                     | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --- | ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D9  | Agent topology            | The orchestrated single Coach (ADR 0007), a single Coach loading skills on demand and a multi-agent topology modelled on ai-running-coach are benchmarked on the same scenarios, knowledge corpus and validator at the end of Phase 1, through subscription CLIs at no API cost, graded blind by judges from three model families outside the generator's family. A pre-registered rule keeps the simplest arm unless a more complex one is clearly better, and offers multi-agent as an opt-in mode with its cost shown when it is better but too expensive ([topology benchmark](topology-benchmark.md), #119). Only synthetic athletes are used. |
| D10 | Topology and model access | Decided 2026-10-14 after the partial [topology benchmark](topology-benchmark.md): plan design and adaptation by the single Coach with skills, no multi-agent delegation; specialist agents (Sports Director, Medical, Course Strategist, Nutritionist) only in conversation workflows, consulted through the Coach, per the [coaching team proposal](coaching-team-proposal.md). Models run through the Anthropic API behind the model gateway (D1); subscription CLIs are used only for development and evaluations. Skills start from ai-running-coach's skills, adapted to Stride, with its MIT notice kept.                                     |

## Risks

| Risk                                                             | Likelihood | Impact | Mitigation                                                                                                                                                                                    |
| ---------------------------------------------------------------- | ---------- | ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plans are valid but not better than a generic template           | Medium     | High   | LLM-judge rubric with seeded-defect calibration; the athlete's own decisions and adherence; downgrade or upgrade models based on evaluation results                                           |
| A plan contributes to an injury or illness                       | Low–medium | High   | Spike and health rules, referral copy, no medical claims, conservative defaults with injury history, low-confidence label above 60 km, clear athlete agency                                   |
| No human expert checks templates, thresholds or health copy (D8) | High       | Medium | Every rule cites its evidence grade; defaults come from the reference project; the athlete reviews every plan; safety scenarios must pass 3 of 3 repetitions; the judge never replaces a rule |
| Thresholds rest on weak or observational evidence                | High       | Medium | Evidence grades on every rule; conventions labeled; thresholds versioned and revisited with observed data                                                                                     |
| Fully detailed weeks drift from reality far from creation (D6)   | Medium     | Medium | The weekly review re-checks the coming week against adherence and readiness and proposes changes; frozen history is never rewritten                                                           |
| Cross-athlete data exposure                                      | Low        | High   | RLS reads as the athlete, scoped tools, private write functions, isolation and injection tests                                                                                                |
| Prompt injection through imported or typed text                  | Medium     | Medium | Data envelopes, no exfiltration tools, validation independent of model reasoning                                                                                                              |
| Cost overrun                                                     | Low        | Medium | Hard per-run caps, usage recorded per call, a provider-side spend limit, kill switch, Batch API for reviews; quotas added only if observed usage requires them                                |
| Approval fatigue from too many proposals                         | Medium     | Medium | One monitor-driven proposal per day, weekly bundling                                                                                                                                          |
| Provider outage, model deprecation or behavior change            | Medium     | Medium | Gateway port, pinned model ids, evaluation gate before upgrades, deterministic degraded mode                                                                                                  |
| Garmin sync delays or gaps                                       | Medium     | Medium | Data-quality gate, freshness in every proposal, change feed (G8)                                                                                                                              |
| The worker role or pooler assumption fails                       | Medium     | Low    | Phase 2 spike first; fallback to a direct connection or a constrained server key as in #42                                                                                                    |
| Worker packaging with `server-only` modules                      | Medium     | Low    | Decide the entrypoint build in the first worker spec; run with the `react-server` condition                                                                                                   |
| Shared Supabase project role still unconfirmed                   | Medium     | Medium | Migrations stay behind the existing approval checkpoint; staging project for live validation                                                                                                  |
| Operations depend on one maintainer and a homelab                | Medium     | Medium | No new stateful service; runbooks; kill switch                                                                                                                                                |

## Open questions without a human expert

D8 removes clinician and coach review, so these questions are answered with conservative conventions, labeled as such, and revisited when evidence or observed data changes:

- Pain and illness thresholds, red-flag list and return-to-running progression.
- Template numbers per event family, long-run caps for ultra distances, masters-athlete adjustments, and the workout library.
- Whether single-session spike limits should use distance, duration or both for trail sessions with large elevation gain.

## Adjacent observation

Stride's race workspace already calls Open-Meteo for weather. Open-Meteo's terms state "You may only use the free API services for non-commercial purposes" and list subscriptions or ads as commercial use ([terms](https://open-meteo.com/en/terms), read on 2026-10-13). This stays compatible with Stride's personal, non-commercial use; a paid plan would be needed only if Stride ever charges athletes.
