# Architecture alternatives and trade-offs

- Status: Accepted (RFC #86)
- Each section lists the options considered, the selected option, why, and what it costs. Versions and limits were verified on 2026-10-12 and 2026-10-13; sources are linked inline.

## 1. Agent topology

| Option                                                                                 | Strengths                                                                                                                                | Weaknesses                                                                                                                                                           |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Five LLM agents with delegation (reference model)                                      | Mirrors a human staff; specialists stay focused                                                                                          | Every delegation is a cold start that re-reads context; disagreements resolved by prose; circular delegation possible; hard to evaluate; cost multiplies per request |
| One LLM agent with tools                                                               | Cheapest, one coherent voice, simple to trace                                                                                            | Prompt grows with every domain rule; no structural check on domain coverage                                                                                          |
| **One Coach agent, deterministic specialists, optional depth-one consults (selected)** | Calculable expertise is code; LLM consults only when judgment is needed; opinions are typed and their constraints become validator rules | Specialist prompts and schemas must be maintained; consult triggers must be tuned by evaluation                                                                      |
| Fully deterministic engine with LLM phrasing only                                      | Most predictable                                                                                                                         | Cannot interpret free text, trade off competing goals or explain choices in context                                                                                  |

Selected because most "specialist" work in the reference is calculation (spacing rules, readiness, course demands, fueling) that is better as tested code, while plan design and multi-race arbitration benefit from model judgment. See [agents and delegation](agents-and-delegation.md) and [ADR 0007](../../adr/0007-coaching-engine-paradigm-and-agent-topology.md).

## 2. Runtime topology

| Option                                                            | Fit                            | Why not selected / selected                                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------------------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Agent SDK embedded in Next.js request handlers                    | Chat answers only              | Plan generation takes minutes; self-hosted Next.js drains in-flight work for 10–30 s on shutdown (`after()` docs in Next.js 16.4), so deploys would kill long runs; privileged credentials would sit in the internet-facing process                                                                                                                                  |
| **Next.js gateway + one coach worker on Postgres (selected)**     | All workflows                  | One extra container from the same image; durable runs; worker holds the provider key and the worker database role; web keeps only athlete sessions                                                                                                                                                                                                                   |
| Dedicated agent API + worker                                      | All workflows                  | A second HTTP service, contract and auth layer without a second consumer                                                                                                                                                                                                                                                                                             |
| Durable workflow engine (Temporal, Inngest, Trigger.dev, Restate) | Long workflows                 | Extra stateful services to run on a homelab: Inngest self-hosting uses Postgres and Redis ([docs](https://www.inngest.com/docs/self-hosting.md)); Trigger.dev v4 needs a webapp, supervisor, Postgres, Redis, registry and object storage and its docs say the guide alone is unlikely to be production-ready ([docs](https://trigger.dev/docs/self-hosting/docker)) |
| Workflow DevKit with the Postgres World                           | Next.js-native durable steps   | Its documentation calls it a "reference implementation … not optimized for scale, speed, or security", with no authentication on workflow HTTP routes and unencrypted stored payloads ([docs](https://workflow-sdk.dev/worlds/postgres)) — unsuitable for health data today                                                                                          |
| DBOS Transact (library, Postgres-backed)                          | Durable steps without a server | Viable later; adds a framework-owned schema and execution model for a workload whose steps are few and already need domain records                                                                                                                                                                                                                                   |
| Headless coding-agent runtime (Claude Agent SDK, OpenCode server) | The reference's chat service   | Built-in file, shell and web tools and per-session workspaces fit one athlete's private workspace, not a multi-tenant product; Anthropic's terms forbid offering claude.ai subscription login through it ([Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview))                                                                                  |
| Supabase Edge Functions                                           | Short tasks                    | 150 s (free) or 400 s (paid) wall clock and 2 s CPU per request ([limits](https://supabase.com/docs/guides/functions/limits))                                                                                                                                                                                                                                        |

See [target architecture](target-architecture.md) and [ADR 0009](../../adr/0009-coach-worker-runtime-on-postgres.md).

## 3. Job queue and run persistence

| Option                                                                                     | Notes                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`agent_runs` as the job record, lease-claimed with `FOR UPDATE SKIP LOCKED` (selected)** | Same pattern garmin_mcp already runs in production for `sync_jobs`; one state machine for domain status and job status; idempotency and singleton constraints are plain indexes                                                                                   |
| pg-boss 12.x (MIT)                                                                         | Mature: retries with exponential backoff, cron, dead-letter queues, SKIP LOCKED, PostgreSQL 13+ ([README](https://github.com/timgit/pg-boss)). Second state store next to domain run records. Documented fallback if fan-out or rich scheduling becomes necessary |
| graphile-worker 0.18                                                                       | Fast, uses LISTEN/NOTIFY; same "second state store" trade-off                                                                                                                                                                                                     |
| Supabase Queues (pgmq)                                                                     | Reachable through the Data API; retries and dead-lettering are left to the consumer                                                                                                                                                                               |
| Redis-based queues                                                                         | A new stateful service                                                                                                                                                                                                                                            |

## 4. Tool interface and data access

| Option                                             | Decision                                                                                                                                                                                                                                                                                                                                                          |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Internal typed tools in the runtime (selected)** | One consumer, one process, Zod schemas shared with domain code, no transport or token audience to manage                                                                                                                                                                                                                                                          |
| A Stride MCP server                                | No second consumer today; would add an HTTP surface, OAuth audience handling (the MCP specification requires servers to reject tokens not issued for them — [security best practices](https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices)) and schema duplication. Reconsider only for an external, athlete-authorized client |
| garmin_mcp MCP tools as the agent's Garmin source  | Rejected for production: live Garmin calls per tool call, contention with sync leases, Garmin-shaped verbose payloads, dependence on a live user token that background runs do not have, and divergence from what the UI shows                                                                                                                                    |
| A generic database or SQL tool                     | Rejected: unbounded privileges and exfiltration surface                                                                                                                                                                                                                                                                                                           |

See [tools and integrations](tools-and-integrations.md) and [ADR 0010](../../adr/0010-internal-tools-and-garmin-normalized-data.md).

## 5. Identity for background runs

| Option                                                                                                                                                                       | Decision                                                                                                                                                                                                        |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Dedicated worker database role that reads as the athlete under RLS (`set local role authenticated` plus JWT claims) and writes only through private functions (selected)** | RLS still applies to every read even if a query forgets a filter; the role cannot read garmin_mcp secrets or other services' private tables; Stride's own database tests already use this impersonation pattern |
| Service-role key with application-level filters                                                                                                                              | Precedent exists for one constrained RPC (#42), but a long-running worker with broad bypass privileges is a larger blast radius                                                                                 |
| Minting a short-lived JWT per athlete                                                                                                                                        | Requires the project's signing secret in the worker and is complicated by asymmetric signing keys                                                                                                               |
| Storing athlete refresh tokens                                                                                                                                               | Rejected: credential hoarding                                                                                                                                                                                   |

The pooler's support for a custom login role is an assumption to verify in the first runtime spike; the fallback is a direct connection or the #42-style constrained key.

## 6. LLM SDK and framework

| Option                                                                                            | Notes                                                                                                                                                                                                                                                          |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Official `@anthropic-ai/sdk` behind a Stride `ModelGateway` port, own bounded loop (selected)** | First-class control of prompt-cache breakpoints, TTLs, effort, structured outputs, strict tools, batches and token counting — the levers the cost model relies on. The loop is small and must persist every step anyway                                        |
| Vercel AI SDK 7                                                                                   | Provider-neutral and Next.js-friendly; majors shipped 2024-11-18, 2025-07-31, 2025-12-22 and 2026-06-25 (npm registry), so a core dependency means a migration roughly twice a year; provider-specific caching and effort controls sit behind provider options |
| Mastra, LangGraph.js, OpenAI Agents SDK                                                           | Framework-owned control flow, memory and storage layers that duplicate Supabase and the proposal ledger                                                                                                                                                        |
| Claude Agent SDK                                                                                  | Coding-agent harness with filesystem and shell tools; see section 2                                                                                                                                                                                            |

Provider portability comes from the narrow port (structured call, tool-loop step, streaming text, token counting) and, more importantly, from the evaluation suite: a new provider adapter ships only when it passes. See [ADR 0011](../../adr/0011-model-access-and-routing.md).

## 7. Plan versioning

| Option                                                             | Notes                                                                                                       |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| Full snapshot per version                                          | Simple reads; a one-session change copies roughly 150 session rows; storage grows with every adaptation     |
| **Revisioned rows with stable keys and version ranges (selected)** | Unchanged rows are shared between versions; any version is a range query; frozen history is a database rule |
| Event sourcing (store operations, replay to read)                  | Elegant audit but every read replays history; harder RLS and indexing                                       |
| One JSON document per version                                      | Easy to diff; no relational adherence, indexing or partial updates                                          |

See [data model](data-model.md) and [ADR 0008](../../adr/0008-versioned-plans-and-proposal-lifecycle.md).

## 8. Model strategy

| Option                                             | Notes                                                                                                                                                                       |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One frontier model everywhere                      | Best quality per call, about 2× the cost of Sonnet-class models on chat and review workloads                                                                                |
| **Tiered routing by task (selected)**              | Opus 5.5 for plan design, Sonnet 5.5 for conversation, adaptation and reviews, Haiku 5.5 for routing, extraction and phrasing; downgrade a route only when evaluations hold |
| Cheapest model plus heavier validation             | Validators catch invalid plans, not mediocre ones                                                                                                                           |
| Multi-provider ensemble or cross-provider fallback | Doubles prompt tuning and evaluation work; deferred until a second provider passes the suite                                                                                |

See [models and costs](models-and-costs.md).

## 9. Progress streaming

| Option                                                                                | Notes                                                                                             |
| ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **SSE route handler reading `agent_run_events` under the athlete session (selected)** | No browser Supabase client (an existing Stride rule); works through Traefik when buffering is off |
| Supabase Realtime                                                                     | Needs a browser client or a server subscription per connection; revisit with load evidence        |
| WebSockets                                                                            | A second protocol for one feature                                                                 |
| Plain client polling                                                                  | Simple but laggy for chat text                                                                    |
